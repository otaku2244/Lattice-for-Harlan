# 历史导入、摘要与索引的规模测量

Lattice 面向个人使用。评估规模时，先区分三件事：保留历史聊天原话、把原话整理成 Event、为 Event／Scene 建立向量索引。它们的数量、资源和耗时不同，聊天条数不能直接换算成向量请求数。

历史文件默认只归档，默认每批最多 25 条；文件预览下的“大批量导入”主动选择最多 250 条一批，长条目受字符预算约束。完整文件仍受 32 MB 上限约束，更大的导出按会话拆分，详见 [导入说明](file-imports.md)。

## 本机归档测量

2026-10-15，Windows，Python 3.13.3，SQLite 3.49.1。本机临时空库、稳定消息 ID 和时间戳、双方交替的短英文合成聊天；不启动 HTTP 服务、不调用模型。表内归档时间不含文件预览。基线使用 `da0a606` 的导入器，在同一解释器与基础依赖上处理同一合成文件。单次样本受磁盘、缓存与其他本机活动影响，不是生产环境时延保证。

| 实现与模式 | 文件条数 | 预览时间 | 完整归档时间 | 归档平均速度 |
| --- | ---: | ---: | ---: | ---: |
| 修改前，25 条一批 | 2,500 | 0.151 秒 | 43.667 秒 | 57 条/秒 |
| 修改后，默认 25 条一批 | 2,500 | 0.240 秒 | 2.770 秒 | 903 条/秒 |
| 修改后，大批量 250 条一批 | 2,500 | 0.152 秒 | 0.389 秒 | 6,420 条/秒 |
| 修改后，默认 25 条一批 | 25,000 | 0.903 秒 | 28.916 秒 | 865 条/秒 |
| 修改后，大批量 250 条一批 | 250,000 | 8.084 秒 | 132.926 秒 | 1,881 条/秒 |

25 万条样本的原始 JSON 为 25.2 MB，完成后的主库为 518.4 MB，包含待导入条目、原话、原始元数据、全文检索及 SQLite 分配的空间。整组测量的 Python 进程峰值占用约 380.2 MB（Windows peak working set，包含生成样本和预览解析）。这些数据不含网页、网关等进程、备份和向量索引，也不是部署内存或磁盘的推荐下限。不同正文长度、附件元数据、会话结构和磁盘会显著改变结果。

这验证了当前实现可以完成这份 25 万条短聊天的归档；没有验证 25 万篇 Scene／Event 的召回延迟，也没有由此给任意长度的记忆库划定推荐条数上限。长对话应按会话拆文件，先完成代表性文件的归档、摘要和索引，再按实际结果安排全量处理。

改善来自：按序号读取当前批次、连接复用、单事务提交、批量查重，以及使查重命中 `(source, source_event_id)` 的非空消息 ID 索引。默认批次不变也能减少本地开销。每批 Scene 的证据 ID 映射只处理本批文档，避免逐条扫描全库证据。

可在源码目录复测，脚本只创建并清理自己的临时实例，不读取实例配置或连接外部部署：

```sh
python scripts/benchmark_file_imports.py --entries 2500 --batch-size 25
python scripts/benchmark_file_imports.py --entries 2500 --batch-size 250
python scripts/benchmark_file_imports.py --entries 250000 --batch-size 250
```

输出包含输入／主库大小、预览／归档时间、平均速度和 Windows 进程峰值占用。每条会保留完整原文和元数据；脚本会确认归档数量准确、没有生成向量待办。增加 `--process-limit 1000` 可以只处理前缀，结果会标明实际处理条数，不能当作完整导入耗时。

## 摘要和向量索引

选择“立即从头摘要（后台）”后，现有后台任务连续推进可处理的批次，不为每一批额外等待自动调度的 30 秒。失败、需修复、待 Agent 或明确暂停时保留已有进度。模型调用数由对话分块、Track、Event 计划、补读及失败重试共同决定，不能把上表归档速度当成摘要速度。

API 执行支持“配置 → 自动摘要配置 → Event Writer 首轮并发数”1–8，默认 1。它只并发 Curator 已确定计划后的首轮 Writer；Router、Curator、补读和结算保持原有顺序，Agent 模式逐个领取任务。可先用代表性文件验证 2 或 4 的成功率和上游限流，再选择合适的并发；本次测试使用模拟模型验证正确性，没有测量真实模型吞吐、费用或总耗时。

“建立／补齐检索索引”已有全量补齐入口，不受后台增量队列默认每轮 100 条限制；正文向量请求默认每批最多 16 篇。只有 Event／Scene 等检索对象进入对应向量流程，历史聊天归档不会逐条生成向量。向量时间取决于最终记忆数、长文分段数、输入长度、模型服务和限流，原有索引锁、失败预算和显式恢复规则保持不变。

页面的速度和预计剩余时间仅覆盖当前文件归档。摘要与索引应分别依据实际处理记录评估，缺少模型吞吐样本时不提供固定完成时间。

## 可选的索引加速

“配置 → 索引处理速度”提供三个独立选项，保存后对下一次索引操作生效；不会开启自动记忆、长文分段或自动摘要，也不改变向量模型、向量空间、召回门槛或证据规则：

| 选项 | 默认 | 可调范围／开启后的行为 |
| --- | --- | --- |
| 向量每批条数 | 16 | 1–64；正文与分段共用 |
| 向量请求并发数 | 1 | 1–4；只并发提供方请求，校验和索引落盘仍由原索引操作执行 |
| 加快后台索引追赶 | 关闭 | 每轮最多取 500 条待办，有积压时等待 0.1 秒后继续；空闲、失败、忙碌时恢复 5 秒检查间隔 |

关闭追赶时仍是每轮最多 100 条、间隔 5 秒。批量和并发需符合提供方限制，可先用代表性文件比较 16 条／并发 1 与 32 条／并发 2。提高并发不保证按比例提速，本地校验、事务提交和提供方限流仍会占用时间。

同一索引操作继续持有原来的跨进程锁。发现请求失败后停止补发，已发出的成功批次先经过原有内容与配置校验再保存；多个失败中如有永久错误则暂停，不因同批的临时错误自动重试。已落盘的批次在恢复时复用；中断仍需显式恢复，不能通过换入口或提高并发重置失败预算。正文或模型配置在请求期间变化时，不保存失效向量。

后台增量处理不再每轮调用全库向量覆盖统计；完整补齐与显式覆盖查询仍返回全库结果。正式实体索引按本轮文档 ID 更新。启用兼容实体 scope 时，其全库同步保持原有证据和 Arc 规则，未改成局部推断。

API 可保存 `recall.embedding_batch_size`、`recall.embedding_concurrency`、`recall.index_catch_up`。TOML 使用相同的 `[recall]` 字段，已保存的实例设置优先。命令行的 `fill-vectors`、`fill-passages` 可用 `--batch-size` 和 `--concurrency` 覆盖保存值。

## 离线索引与 Writer 测量

同日、同机、相同 Python／SQLite，使用临时空库和模拟提供方，真实模型调用数为零。索引样本为 400 篇短 Event、2 维假向量，每次请求固定等待 40 毫秒；耗时包含准备、校验、提交和覆盖统计。它验证程序的批量与并发行为，不代表真实模型速度、向量质量或计费。

| 向量每批条数 | 请求并发 | 请求次数 | 完整补齐耗时 |
| ---: | ---: | ---: | ---: |
| 16 | 1 | 25 | 2.265 秒 |
| 16 | 2 | 25 | 1.441 秒 |
| 16 | 4 | 25 | 1.325 秒 |
| 64 | 2 | 7 | 1.288 秒 |

增量调试中，原实现只更新 100 篇，却在 2,500 篇库上花约 0.767 秒检查全库覆盖。移除这次无关统计后，相同的 100 篇更新在 100 篇库上约 0.361 秒、2,500 篇库上约 0.402 秒；这组样本未启用兼容实体 scope，不能外推为所有索引阶段都不随库大小增长。

Writer 样本为一批 8 条合成原话，使用内联模拟执行器，经真实归线、Curator、Writer 与结算流程生成 4 个 Event；每次模拟模型调用固定等待 250 毫秒。三种并发均为 1 次 Router、1 次 Curator、4 次 Writer，并保留 8 条证据绑定：

| Writer 首轮并发 | 整批耗时 | 实测最大同时 Writer 数 |
| ---: | ---: | ---: |
| 1 | 2.133 秒 | 1 |
| 2 | 1.910 秒 | 2 |
| 4 | 1.263 秒 | 4 |

该测试验证已有的 Writer 并发路径及生成结果数量，不评估真实模型的写作质量，不把 Router、Curator 或后续补读并行，也不据此估算 25 万条历史的摘要总耗时。

复测命令（将并发改成 1、2、4 可分别比较）：

```sh
python scripts/benchmark_memory_jobs.py --kind index --owners 400 --batch-size 16 --concurrency 2 --delay 0.04
python scripts/benchmark_memory_jobs.py --kind index --owners 2500 --target 100 --delay 0
python scripts/benchmark_memory_jobs.py --kind writer --concurrency 4 --delay 0.25
```
